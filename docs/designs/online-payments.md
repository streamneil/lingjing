# CEO Plan: 收银台在线支付(微信支付 + 支付宝)

## Vision

### 10x Check
这不只是加一个付款按钮——是平台从「运营人工收钱」变成「自助收银机」的转折点。
当前充值唯一路径是对公转账 + 超管人工核对(最长 1 个工作日,用户旅程明确标注
「焦虑:钱到了吗」)。在线支付把到账压到秒级,把超管从核对工作里解放出来。
通道抽象层(`src/payments/`)落地后:支付宝是第二个 Provider 实现类、席位自助
升级(T-SEAT-BILLING)是第二个商品类型、任何未来付费能力(增值包、私有化
license)都走同一通道层。收银台从充值专用变成全平台交易入口。

### 实现方案(0C-bis 定稿:Approach B)
通道抽象层 + Native/H5 双场景:
- 新建 `src/payments/`:PaymentProvider 接口(创建支付 / 查单 / 回调验签 / 关单 / 退款),
  微信为首个实现,支付宝同轮第二个。
- PC 出二维码(Native,code_url),手机浏览器出 h5_url 拉起微信;支付宝对应
  电脑网站支付(page)/ 手机网站支付(wap)。
- 加密手写(微信 v3:RSA-SHA256 签名 + 微信支付公钥验签 + AES-256-GCM 回调解密;
  支付宝:RSA2),零新依赖(项目一贯依赖极简,undici 已在)。
- 超管后台配商户号/密钥(循 payee_setting 不进 git 范式);**未配置时收银台该通道
  保持「敬请期待」占位——满足「先开发、后配置」交付要求,配置一填即上线**。
- 到账:支付回调(验签+幂等)+ 前端轮询查单双保险。
- 复用存量钱路加固:transitionOrder 原子迁移、credit_ledger(order_id) 部分唯一索引、
  套餐快照、scopeByActor、audit。

## Accepted Scope (added to this plan)
- 基线:微信支付 Native(PC 扫码)+ H5(手机浏览器),`src/payments/` 通道抽象层,
  超管后台商户配置(未配置=占位),回调入账 + 轮询查单,订单台账/admin 展示
- 支付宝:电脑网站支付 + 手机网站支付,同一通道层第二实现
- 退款闭环:超管后台发起 → 通道退款 API → 退款结果确认(微信=异步回调,
  支付宝=同步响应,通道层统一抹平)→ ledger 追回 → 订单 refunded 态;
  出钱方向,与入账同等幂等/金额护栏。**v1 仅整单全额退款,部分退款延后**。
  余额可负:负余额下新任务 reserve 失败(积分不足),服务自然停用直至再充值——
  复用现有 reserve 语义,无需新增封禁逻辑
- 每日对账:拉双通道对账单 vs 本地订单,差异落表 + 超管后台告警。
  v1 告警面 = 超管后台差异面板 + 服务端 error 级日志(可被日志监控拾取);
  主动推送(短信/邮件)随「到账通知」基建下轮补——明确接受 v1 差异发现
  依赖超管登录查看,这是有意的取舍而非疏漏
- 微信内置浏览器场景:v1 不做 JSAPI 支付(需公众号 openid 体系,独立一条线);
  检测微信 UA 时展示 Native 二维码 + 「长按识别二维码支付」引导(微信长按可识别
  code_url 收款码),并提示可用系统浏览器打开走 H5——死路兜底,入体验包
- 迟到回调 vs 2小时自动取消:自动取消 sweep 对在线单先查单——已支付→直接入账,
  未支付→调通道关单(closeOrder)再取消。成功回调命中**已取消/已关单**订单 →
  拒绝入账、落对账差异表并告警,由超管用退款闭环对该笔原路退款;
  命中**已入账(credited)**订单 = 微信/支付宝正常重试投递,走幂等路径静默应答
  SUCCESS(行级条件 UPDATE changes=0,不告警不退款)——钱只进不丢,静默失败为零
- 体验包:①二维码/h5_url 倒计时+过期一键刷新 ②支付成功即时变绿+余额跳动
  ③台账「秒到账」徽章 ④支付方式记忆 ⑤H5 返回自动检测结果

## Key Constraints(实现必守)
- 金额单位:订单是元,微信/支付宝 API 是分——换算收敛到通道层单一点,带护栏测试
  (prior learning:钱路曾因单位错出过 134× 事故)。
- 微信单/支付宝单跳过 paid_claimed 人工核对态:pending_payment → credited 由回调驱动,
  行级条件 UPDATE 保幂等;credited 终态语义不变。
- 回调端点无登录态(靠验签),验签失败返回 4XX 让平台重试;金额不符拒绝入账并告警。
- 出网走代理场景:新增 ENV 必须同步 docker-compose.yml 转发(prior learning:
  OPENAI_PROXY 漏转发事故)。
- 支付宝商户资质申请周期可能长于微信——代码不阻塞,未配置即占位。

## 评审定稿决策(11-section 评审 + Outside Voice,全部经用户拍板)

1. **payment_attempt 独立表**:每次支付尝试一行(channel/out_trade_no/状态/金额分快照);
   订单只记最终 payment_method。对账逐笔对平、退款精确引用。
2. **支付方式 pending 期可切换**:切换/刷新时对旧 attempt 调通道关单,实际支付成功/
   claimPaid 时锁定;关单失败提示已付→查单入账。
3. **商户密钥复用现成基建**:src/gateway/key-crypto.ts + MASTER_KEY(已在 compose、
   admin UI 带 last4 回显)。不新增 PAYMENT_MASTER_KEY ENV。
4. **幂等按交易号**(双重支付防线):同 out_trade_no 重投递→ACK;credited 单上
   **不同交易号**的成功回调 = 双重收款→落差异表+告警+原路退款。
5. **退款×发票拦截**:订单挂在任何发票上(requested/issued)拒绝退款,提示先驳回发票;
   refunded 态补进 adminOrderCounts 等所有状态枚举。
6. **建单守卫改「至少一种可付方式已配置」**:按所选方式分别校验,替代 PAYEE_NOT_READY
   硬性对公检查。
7. **H5 按场景独立开关**:每通道 Native/H5 分开启用(H5 需单独审批+ICP 授权域名);
   H5 未开时手机端回退 Native 码+长按识别引导。
8. **用户触发主动查单**:POST /orders/:id/check-payment(限流,每单每 3s),
   「我已支付」点击 + H5 返回页自动触发,实时查通道,已付即刻入账。
9. **回调传输**:回调路由 express.raw(微信,验签需原始字节)/urlencoded(支付宝)
   先于 json parser;每通道 ACK 格式(微信 JSON / 支付宝字面量 success)进 Provider 接口。
10. **ledger 新增 kind='refund'**:镜像 grant 的 order_id 部分唯一索引;显式排除出
    usageSummary/consumed 消耗统计公式。
11. **退款对象是 payment_attempt**:通道退款按 attempt;ledger 追回仅当订单曾 credited
    (覆盖「已收款未入账」的迟到回调单)。
12. **out_trade_no = attempt id**,永不用 order_no(微信禁止复用已关单号)。
13. **sweep 查单路径完整具备入账能力**(同 transition+grant),私有化内网(无回调)下
    是唯一入账路径。

### 接口签名(src/payments/)

type Channel = 'wechat'|'alipay'; type Scene = 'native'|'h5'|'page'|'wap';
interface PaymentProvider {

  queryPayment(attemptId): Promise<{status: 'not_found'|'pending'|'paid'|'closed'; txnId?; paidAmountFen?; paidAt?}>;

    event: 'payment'|'refund'; ack: {status; body; contentType}}>;   // ACK 进接口(决策9)

  refund(p: {attemptId; txnId; refundNo; amountFen; reason}): Promise<{status: 'processing'|'succeeded'|'failed'; reason?}>;
}

### Eng Review Outside Voice 增补(2026-07-13,14 条全采纳)
18. **out_trade_no = 去横杠 UUID(32 hex)**——微信 out_trade_no 上限 32 字符,原生 UUID 36 字符必被拒。
19. **PaymentProvider 加 `downloadBill(billDate): Promise<BillRow[]>`**(归一行:outTradeNo/txnId/amountFen/status),对账在通道抽象层后实现。
20. **verifyNotify 返回补 `refundNo?/refundStatus?('succeeded'|'failed')/refundAmountFen?`**——微信退款结果是异步通知,applyRefundResult 由回调驱动。
21. **退款时序钉死**:同事务「挂票检查 + transitionOrder(credited→refunding)」先于通道调用(堵 TOCTOU:空窗内 requestInvoice);通道失败 → refunding→credited 回退 + attempt→refund_failed,订单不卡死。
22. **对公×在线互斥(3A)**:applyPaymentSuccess 接受 from ∈ {pending_payment, paid_claimed}(钱到即入账,与超管 confirm 由行级条件 UPDATE 保恰一次);有在途 attempt 时 claim-paid 拒,paid_claimed 后 startPayment 拒。
23. **每单恰一在途码**:`CREATE UNIQUE INDEX ON payment_attempt(order_id) WHERE status='pending'`;startPayment 同事务关旧插新(通道 closeOrder 在 commit 后)。
24. **过期锚点对齐**:`expires_at = min(场景 TTL, order.created_at + PENDING_PAYMENT_TTL_MS)`,并作为 time_expire 传通道——堵「复用旧单出的码比订单多活 2h」。
25. **recon_diff 幂等**:`UNIQUE(channel, out_trade_no, txn_id, kind)` + upsert;拒绝入账但差异已记录的回调 → **ACK SUCCESS**(否则微信重试数天刷屏差异表)。
26. **新增 ENV `PUBLIC_BASE_URL`**(notify/return URL 基址):进 .env.example + docker-compose 转发;未配置 → 在线通道占位(同 MASTER_KEY 降级)。
27. **sweep 异步化防重入**:in-flight 守卫(上轮未完跳过本 tick)+ 单单 try/catch。
28. **transitionOrder patch Pick 扩宽**:+ payment_method(付款锁定)等,不许绕单一门裸 UPDATE。
29. **createPayment 补 `returnUrl`**(H5 返回/支付宝 quit_url);返回 `{kind: 'qr'|'redirect', payload}` 区分二维码内容与浏览器跳转。
30. **回调入账写系统 actor 审计**:applyPaymentSuccess/applyRefundResult 记 audit(actor=system:payment),线上入账不从审计轨迹消失。
31. **测试清单 +6**:checkPaymentNow×回调并发、并发 startPayment 恰一 pending、recon 重跑幂等、微信退款通知验签向量、claimPaid 后回调入账、旧单复用×过期锚点。partial index 改为 `(expires_at) WHERE status='pending'`(sweep 按过期时间扫)。
